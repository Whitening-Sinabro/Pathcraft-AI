## 1. 사용자가 처음 만나는 흐름

첫 화면은 긴 상담이나 모델 응답을 기다리지 않고 다음 짧은 선택지를 보여 준다. 아래는 구현할 질문안이며 지금 사용자에게 답을 요청하는 설문이 아니다. 최초 5항목은 한 번의 짧은 선택 화면으로 묶는다. **기본 응답 1분 이내**를 아직 측정하지 않은 사용성 검증 목표로 두며, 후보 전 추가 질문은 추천을 바꾸는 필수값에 한정한다. 선호나 보유품 전수조사로 늘리지 않는다.

버튼 수·조작 선호는 카탈로그 후보를 실제로 갈라야 할 때 한 번 더 묻는다. 기존 캐릭터에서 클래스/레벨이 누락되거나 선택한 전환이 특정 장비·자원에 의존할 때만 추가 질문한다. 예산은 구매가 필요한 단계, 보유품은 핵심품/허용대체 확인 시점에 받는다. 예산 미상을 3 divine이나 0으로 치환하지 않는다. 자동 스태시 연동은 선행조건이 아니다.

**후보 화면:** 준비된 카탈로그에서 game/patch/두 모드 축/기존 캐릭터 제약/필수 운용 조건을 먼저 필터링한다. 통과한 후보에만 조작 선호 등을 적용해 순위를 정한다. 카드에는 추천 이유, 조작 부담, 시작 가능한 구간, 필요한 준비, 검증 범위를 짧게 표시한다. 2~3개를 채우기 위해 부적합 후보를 넣지 않는다. 1개면 1개, 0개면 이유와 지원되는 범위를 즉시 표시한다. 모드가 미정이면 이를 명시한 탐색 카드만 보여 주고 확정 생성 전에 결정한다.

**선택 후 첫 가이드:** 사용 가능한 시작 단계, 실제 스킬·보조 연결, 장비/패시브 구성, 무기세트, 다음 전환 조건과 확보 순서를 보여 준다. 허용된 대체품과 현재 조건에 맞춰 실제 구성·단계가 달라져야 한다. 링크나 정적 설명만 반환하지 않는다. 캐릭터 진행은 어느 단계부터 볼지를, 이해도는 설명 깊이를, 플레이시간은 체크포인트를 바꾼다. 이 세 값을 공격·생존 적합성의 대용으로 쓰지 않는다.

## 2. 사전 준비와 즉시 응답 경로

| 경로 | 처리 순서 | 대기·실패 처리 |
|---|---|---|
| 준비/갱신 작업 | 기존 방송·배포 가이드·실측 수집본 대조 → 정정/충돌 해결 → claim·condition·stage 구조화 → 목표 패치 영향 확인 → 독립 검수 → 버전 고정된 카탈로그 배포 | 새 수집이 필요한 공백만 별도 작업 큐에 등록. 미해결 범위는 보류하며 사용자 요청을 붙잡아 두지 않음 |
| 사용자 응답 | 로컬 배포 카탈로그 조회 → 적합성 필터 → 후보 선택 → 승인된 변형/단계 구성 → 규칙 판정 → 첫 가이드/독립 저장 → 선택적 설명 보강 | 요청 중 신규 방송·영상·웹 수집 0회. 자료 없음/충돌/오래된 패치면 즉시 이유·지원 범위·현재 단계 유지 또는 보류 반환 |

로컬 팩을 번들·캐시해 서버와 설명 API가 꺼져도 지원 범위 안의 핵심 경로를 제공한다. 최신 버전 확인에 실패하면 설치된 버전·마지막 확인 시각을 표시한다. 사용자가 지정한 패치와 동등성이 확인되지 않은 팩은 현재 추천으로 승격하지 않는다. 이전 버전은 참고 열람할 수 있어도 현재 패치의 승인 결과로 표시하지 않는다. 승인 팩이 하나도 없으면 ‘추천 없음’을 정상 응답으로 처리한다.

LLM은 설명의 길이 조절과 필요한 질문의 표현을 돕는다. 사실·유효성·핵심 전환 조건과 승인 여부는 구조화된 근거·규칙이 결정한다. 핵심 결과는 결정적 템플릿으로 먼저 그리고 설명은 나중에 붙인다. LLM 출력이 정본 구성·조건·수치를 변경할 권한을 갖지 않게 한다. 공격/생존 수치는 출처·측정/계산 방법·조건이 일치할 때만 표시하고 그 외에는 미확인으로 남긴다.

새 공통 계약의 필수 단위는 아래와 같다. 파일 이름보다 계약과 승인 상태를 먼저 확정한다.

| 허용 변형과 근거 | 대체 젬/장비/패시브의 적용 조건·상호배제·재검증 범위, 공격·생존·자원·확보 근거. 고정 수치는 조건부 값으로 보존하며 제작자 관측 성능을 사용자 예상치로 복사하지 않음 |

**초보자 안내의 재사용 단위:** 게임·패치별 공통 안내(캠페인 진행 중 필요한 젬·자원·무기세트 등)와 빌드별 단계·전환 설명을 분리한다. 공통 안내도 ID·출처·패치·확인 상태를 가진 검증팩 계약 및 M2 산출물에 포함하고, 각 stage가 필요한 시점에 해당 ID를 참조한다. 기존 검증자료를 재사용해 같은 기초 설명을 빌드마다 다시 조사하지 않는다. 없는 스토리·퀘스트 정보는 미확인으로 남기고 LLM이 채우지 않는다.

**첫 정본화 대상:** 두 사례의 근거서와 연결된 실제 산출물을 사용한다. 임성빈은 계획·Lv61·후기 export·방송 정정을 분리하고 전환 능력치/비용/세트 조건을 보존한다. 스카두쉬는 구판 토템 6레벨 대 최신 7레벨, 시작 단계 대 완성 목표의 요구 레벨, 05/06 트리 개정, 07 트리/젬 시점 혼합을 먼저 정리한다. 최신 문구를 무조건 채택하기보다 근거·대상 버전·조건이 일치하는지 판단한다. 해결되지 않은 조건을 가진 변형/단계는 보류한다. 두 팩의 모든 단계 승인을 기다릴 필요 없이 충분한 근거가 있는 제한된 시작 구간부터 승인할 수 있다.

승인 상태는 팩 전체의 단일 PASS로 끝내지 않는다. 핵심 gate의 근거가 충족되고 구성 요소 간 충돌이 없으며 승인 범위가 표시된 경우에만 해당 variant/stage를 후보로 공개한다. **버전 pin:** 생성 revision은 pack version·claim IDs·규칙 버전을 고정 참조한다. 정정/패치가 들어오면 의존 claim→조건→변형/단계를 따라 영향 범위만 갱신필요로 전환한다. 이전 결과를 조용히 바꾸지 않고 ‘재확인 필요’와 변경 이유를 보여 주며 재검수 후 새 revision을 만든다. 저장 재열기도 카탈로그 상태를 확인하고, 연결이 없으면 마지막 확인 시각을 숨기지 않는다.

**사전 조사도 간소화한다:** 순서는 **① 기존 자료 우선 → ② 핵심 조건 대조 → ③ 충돌·필수 누락 구간의 영상만 확인 → ④ 패치 영향 항목만 재확인**이다. 이미 있는 제작자 가이드·단계 파일·게임 데이터를 먼저 재사용하고, 빌드 작동과 전환을 바꾸는 핵심 주장만 대조한다. 충돌·필수 누락이 남은 구간만 영상을 표적 확인하며, 패치 변경 때도 영향받은 주장·단계만 재검증한다. 전체 방송 시청이나 전수 프레임 판독은 팩 등록의 공통 필수가 아니다. 승인표에는 난도·모드·진입/전환·필수 장비·대체안의 근거와 함께 카탈로그 커버리지 공백을 적는다. 첫 두 사례가 모든 신규 사용자 분류를 채운다고 가정하지 않는다.

**다른 스트리머 확장:** 사용자 수요가 있고 기존 팩이 못 채우는 운용/진행 범위이며 출처와 단계 구성이 확보 가능한 사례부터 고른다. 자료 수·방송 길이를 목표로 삼지 않는다. 충분증거 기준은 지원하려는 각 단계의 필수 구성·진입/전환 조건·획득/대체·주요 자원/생존 제약에 추적 가능한 근거가 있고 모순이 해결된 상태다. 중요한 전환 주장은 배포 가이드와 실측 등 다른 근거를 대조한다. 없으면 지원 범위를 줄이거나 보류한다. 모든 영상·모든 클릭을 복원할 필요는 없다. 핵심 주장이 충족되고 추가 조사로 승인 판단이 바뀌지 않으면 조사 종료; 해결 안 되는 핵심 충돌은 담당자가 정한 조사 한도에서 보류하고 외부 수집을 끝낸다.

### 시즌 전환: 기존 사례로 절차를 만들고 새 시즌 팩을 재승인한다

**우선순위:** 1.0.0 전에는 현 시즌 빌드를 전수 확장하기보다 팩을 교체할 수 있는 제품 구조와 기존 두 사례의 고정 테스트 기반을 먼저 만든다. 화염파·스카두쉬는 현재 자료로 구성·검증 절차를 시험하는 사례이며 **1.0 추천 상품으로 확정하지 않는다.** 둘 다 추천 중지되더라도 입력→판정→저장·출처 추적 절차는 유지되어야 한다. 생존 빌드 비율·일정·구체적 패치 결과는 예측하지 않는다.

짧은 입력, 독립 저장, 출처 추적, 규칙 실행 구조는 재사용하되, 젬·패시브·스탯·장비·획득/경제·캠페인·전환 순서는 패치별 내용으로 분리한다. 공통 메카닉·스토리 안내도 버전과 적용 범위가 있는 교체 대상이다. 필수 메카닉/획득 조건·게임 dataID→팩 claim→조건/단계/변형→생성 revision의 의존관계를 관리하고, 공통 안내 변경도 이를 참조하는 단계에 전파한다.

**1.0 목표 추천은 모두 미승인에서 시작한다.** 패치노트에 언급이 없다는 이유로 승인하지 않는다. 변경 선별은 검수 우선순위를 정하는 도구이며 동작 보증이 아니다. 각 범위를 유지 후보 / 조건 수정 / 재제작 / 보류로 분류한 뒤, 핵심 상호작용·자원·트리·획득·레벨링 전환을 공식 정보·실제 빌드 데이터·필요한 표적 실사용 확인으로 대조해 재승인한다. 유지 후보도 재승인 전에는 공개 추천하지 않는다. 원본 팩과 기존 결과의 version pin을 보존하고 승인된 일부 단계부터 새 시즌 팩으로 열 수 있다. 이전 결과는 당시 버전의 참고용으로 열람하되 새 시즌 사용 가능과 구별한다.

| 준비 시점 | 사용자 요청 밖에서 수행할 일 |
|---|---|
| 1.0 직전 | 공식적으로 확인 가능한 변경만 반영해 의존관계·검수 목록과 팩 교체/중지 절차 준비. 정보 부족 항목은 미승인 유지 |
| 당일 | 실제 데이터의 ID·조건 차이와 핵심 작동/획득을 표적 확인하고 후보 공개 상태 결정. 출시 즉시 모든 빌드의 완전 검증·추천을 약속하지 않음 |
| 초기 안정기 | 충분히 확인된 소수 범위부터 단계별 재승인, 수정/실사용 근거에 따라 팩 교체·재검수. 새 자료 없이 범위를 늘리지 않음 |

승인 후보가 없으면 즉시 현재 지원 범위와 ‘새 시즌 준비 중’을 표시한다. 과거 팩은 명시적 버전 참고로 남기고, 사용자마다 영상 재조사를 기다리게 하지 않는다. 다음 구현의 우선순위는 두 고정 사례→교체 가능한 구조→시즌별 승인 팩이며 특정 빌드의 존속에 제품 전체를 의존시키지 않는다.

## 6. 첫 완주 수용조건과 응답시간 목표

아래는 **향후 구현에서 실행할 검사 계획**이다. 이번 문서 작업에서는 테스트를 실행하지 않았다.

| 시나리오 | 수용 결과 |
|---|---|
| 승인 팩으로 새 캐릭터 생성 | PoB·외부 수집 없이 후보를 선택하고 스킬/지원·장비/대체·패시브·시작 단계/전환·근거가 있는 결과와 첫 할 일을 받음 |
| 조건 변경 최소 2개 | ① 팩에 승인된 예산/보유 핵심품 유무 변경 → 실제 장비·대체·전환 변경, ② 확보 젬/소켓 또는 현재 단계 변경 → 실제 연결/할 일/순서 변경. 설명만 바뀌면 불합격; 해당 변형 승인 없으면 임의 조합하지 않고 다른 승인 사례를 선택 |
| 불가능 조건 최소 1개 | 예: 핵심품 없고 허용대체도 없음 → 전환 거절과 현재 단계 유지/지원 범위 반환. 성공 저장/내보내기로 오인되지 않음 |
| novice / veteran | 같은 게임 조건이면 구성 적합성 기준은 같음. 설명 길이·체크포인트만 달라지고 경험만으로 HC 적합성을 판정하지 않음 |
| 모드·후보 경계 | HC+SSF를 독립 평가, 거래 필수품에 의존하는 후보 제외. 0개는 정상 보류, 1개는 그대로 표시; 부적합 후보로 수 채우지 않음 |
| stale·정정·API 장애 | patch 비동등/핵심 claim 정정 시 영향 결과에 재확인 표시. 외부 API 전면 차단·설명 지연에도 로컬 승인 범위 핵심 결과 또는 즉시 보류 제공 |
| 저장·재열기·변경 이유 | PoB 없는 새 ID 저장, 과거 PoB 입력 후 새 생성이 이전 기록을 덮지 않음. 재열기 시 game/patch/두mode/revision/구성/출처 동일. 두 변경의 원인·차이·판정 추적 가능 |

**아직 측정하지 않은 목표:** 명시한 기준 Windows PC와 로컬 승인 팩에서, 필요한 입력 제출→후보/0후보 결과 p95 1초 이내, 후보선택·필수조건 확정→첫 구조화 가이드 p95 2초 이내를 목표로 잡는다. 이는 달성 사실이나 출시 SLA가 아니다. 측정은 UI 이벤트부터 실제 표시까지, 최초/반복 실행을 분리하고 표본 수·캐시·팩 버전을 기록한다. 목표를 못 맞추면 수집을 동기 경로에 추가하는 대신 로딩 단계·카탈로그/구성 비용을 조정한다. 설명 지연은 핵심 가이드 표시 시간을 늘리지 않아야 한다.

관찰 가능한 고정 조건은 **사용자 요청 중 신규 외부 수집 0회**, 외부 API 차단 시 무기한 대기 0건, 요청별 승인/보류 이유 존재, 미검증 성능 수치 0건이다. API 호출 수·핵심 결과/설명 도착 시각·저장 오류를 분리 계측한다. 기간·완성률은 추정하지 않고 위 통과 조건으로 진척을 판단한다.

모두 기본 모델은 gpt-6-astra로 제안하며 실제 배치 때 역할별 model/effort를 명시하고 receipt에서 요청/실효 설정을 확인한다. 전역설정은 바꾸지 않는다. 작업자는 필요 시 최소 인원으로만 운영하고 초기에는 데이터와 앱/생성 두 역할을 병렬, 독립검수는 산출물이 준비되면 투입한다. 같은 파일에 여러 역할이 동시에 쓰지 않도록 중간책임자가 소유권을 나눈다. 새 checkout을 평가대상 대체품으로 취급하지 않으며 향후 구현 위치·동시 편집 충돌은 착수 시 기존 작업트리 상태에 맞춰 정한다.

각 마일스톤은 산출물·검사 증거·남은 미확인을 보고하고, 검수 전 완료 선언을 하지 않는다. 추가 웹/영상 확인이 필요하면 준비 작업 큐로 보내며 사용자 요청 경로를 막지 않는다. 현재 적용된 세션 운영 지침에 따라 완료 작업자는 retain하고 사용자 명시 종료 없이 close/worker-release 등 간접 종료를 하지 않는다. 기존 완료 dispatch 정산은 변경하지 않는다.
